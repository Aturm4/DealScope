# Архитектура

DealScope состоит из локального Python-приложения, SQLite-хранилища и
веб-интерфейса на HTML/CSS/JavaScript. Сервер интерфейса слушает loopback;
Telegram-транспорт подключается вручную отдельным сценарием.

## Поток данных

1. Выбранный источник отдаёт новые публикации и правки.
2. Парсер извлекает цену, валюту, объём и явно указанные характеристики.
3. Правила возвращают подходящее, исключённое или требующее проверки предложение.
4. SQLite хранит исходный текст, версии, решения и состояние очереди.
5. Интерфейс показывает причину решения и состояние источника.
6. Отдельный бот доставляет новые совпадения подтверждённому владельцу.

Сохранение версий, пересчёт фильтров и отправка уведомлений разделены.
Пересчёт старой истории не создаёт новые отправки.

## Каталоги

| Путь | Назначение |
| --- | --- |
| `dealradar/parser.py`, `filters.py`, `models.py` | Разбор и правила |
| `dealradar/storage.py` | SQLite и версии публикаций |
| `dealradar/notifications.py`, `notification_store.py` | Очередь и результаты доставки |
| `dealradar/telegram_*.py`, `bot_*.py` | Транспорт, ручной вход и уведомления |
| `dealradar/web_app.py`, `web_store.py` | Локальный HTTP API и представление данных |
| `dealradar/web/` | Общие UI-файлы |
| `site/` | Необязательный статический Sites-компаньон |
| `examples/` | Синтетические офлайн-примеры |
| `tests/` | Офлайн-регрессии, локальный API и транспортные фикстуры |

## Приватный компаньон

Статическая страница Sites обращается к API работающего локального процесса
после явного подключения временным кодом. SQLite и Telegram-транспорт остаются
на ПК. Origin и запросы проверяются сервером; публичный сетевой listener
для локального API не используется.

## Данные и полномочия

Telegram-сессия и токен бота находятся в памяти процесса. SQLite содержит
историю объявлений, настройки и подтверждённые идентификаторы; база не зашифрована.
Подробности ограничений — в [SECURITY.md](../SECURITY.md).
